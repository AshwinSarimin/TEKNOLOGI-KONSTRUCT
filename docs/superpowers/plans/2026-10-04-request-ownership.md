# Finding #1: authenticated request ownership

Approved in conversation on 2026-10-04. Implementation stays on the current
feature branch; Ashwin handles commits and pushes. Backstage live promise flows
remain deferred.

## Design

- Keep the verified five broker-only RoleBindings.
- REST API: replace shared `API_KEY` with `API_KEYS`, a JSON object mapping stable
  caller IDs to distinct bearer tokens. Fail startup on ambiguous/invalid config.
- Derive `teknologi.io/request-owner` from authentication: `rest-api:<caller-id>`
  or `backstage:<authenticated-user-entity-ref>`. Never trust a supplied owner.
- Allow only the five request kinds, version `marketplace.kratix.io/v1alpha1`, in
  `kratix-workloads`. Require named requests with object-shaped specs.
- Create when absent. For an existing request require an exact owner match and
  a resourceVersion-guarded update retaining UID and controller metadata. Deny
  unowned, differently owned, and terminating requests. Return conflicts to callers
  rather than retrying an unchecked write. Remove REST API force-apply.
- Owner is immutable through both brokers. Administrators remain trusted; no
  implicit migration/adoption of legacy requests. Each Backstage user owns their
  submissions; a REST caller can represent one team's automation. Cross-channel
  identities intentionally differ. Sharing/transfers require administrator action.
- This governs request objects. Competing infrastructure generated by different
  request names is finding #4 and remains separate.

## Review focus

Ownership must survive key rotation, cannot be supplied via request metadata or
the Backstage template, and must be rechecked on every write. Preserve Kubernetes
resourceVersion/UID so deletion/recreation and concurrent changes cannot bypass
the check. Fail closed on authentication/config/Kubernetes errors. Do not silently
adopt existing unowned requests, copy arbitrary template metadata into updates,
or claim local tests establish deployed behavior.
